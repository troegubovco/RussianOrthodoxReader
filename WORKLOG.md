# WORKLOG

Журнал работ по «Синодалу». Новые записи — сверху.

Что сюда пишется:
- каждый созданный файл с одной строкой о его назначении (отсюда
  `architecture-update` потом поднимает нужное в [ARCHITECTURE.md](ARCHITECTURE.md));
- решения и их причины — особенно те, что не выводятся из кода;
- тупики: что проверено и не сработало, чтобы не возвращаться;
- то, что осталось незакрытым.

Что сюда не пишется: пересказ диффа, косметика, всё, что и так видно в
`git log`.

Формат записи:

```
## YYYY-MM-DD — Короткий заголовок

**Сделано.** …

**Новые файлы.**
- `путь/к/файлу` — назначение в одну строку.

**Решения.** … (и почему)

**Открыто.** …
```

## 2026-09-02 — Планы чтения: заметный вход, переход из «Моих чтений», остановка; пустой экран акафистов

**Сделано.**

- В списках «Акафисты» и «Псалтирь» — подсказка одной строкой, как начать план.

**Открыто.**

## 2026-09-02 — Акафисты, Псалтирь и «Мои чтения» (планы с кольцом прогресса)

**Сделано.**
- *Акафисты* — новый раздел молитвослова `akafisty`, 12 акафистов (Иисусу
  Сладчайшему, Пресвятой Богородице, Николаю, Пантелеимону, Ангелу
  хранителю, Матроне, Сергию, Серафиму, Спиридону, Покрову, «Слава Богу за
  всё», Иоанну Предтече), по одной записи на акафист с рубриками
  `*Кондак N*`/`*Икос N*` и заключительными молитвами. На телефоне —
  «Содержание» в тулбаре (при ≥8 рубрик — достаётся и канонам), на часах
  фрагменты режутся по кондакам сами.
- *Псалтирь — две двери.* Текст церковнославянский гражданским шрифтом —
  раздел молитвослова `psaltir` (молитвы перед чтением, 20 кафизм с
  «Славами» и своими тропарями/молитвой по кафизме, молитвы по окончании,
  Псалом 151). Навигация «по кафизмам» — во вкладке Библии поверх
  синодального текста: карточка «Псалтирь по кафизмам», лист с 20 кафизмами
  и «Славами», новый сохраняемый маршрут `ReaderRoute.kathisma`, в читалке —
  разделители «Слава» (по касанию — молитвы после «Славы»), кнопки «ЦС» и
  «Молитвы по кафизме».
- *Великий канон прп. Андрея Критского* — четыре части (Пн–Чт первой
  седмицы) в «Канонах», ЦС + перевод.
- *Планы чтения с кольцом.* Акафист **не дробится**: единственный
  многодневный режим — читать целиком каждый день N дней (7 / 12 / 40 / до
  конца поста / своё). Дробятся по дням только Псалтирь (по кафизме — 20
  дней, по «Славе» — 60) и Великий канон (4 части). Модель `ReadingPlan` +
  отдельная запись на каждую отметку (растущее множество, без потерь при
  одновременных отметках), SwiftData + CloudKit (`ReadingPlan`,
  `ReadingPlanUnit` в `PrayersZone`), ≤3 активных планов, напоминания в
  бюджете уведомлений. UI: `ProgressRingView` (общий для iPhone и часов),
  карточка плана над текстом, «Прочитано сегодня» под текстом, лист выбора
  плана с формулировкой практики, лист «догнать» пропущенные дни (без
  красного и «провалов»), карточка «Мои чтения» на корне молитв и — только
  псалтирные планы — на корне Библии. Часы: строка с кольцом на корне, экран
  плана, «Прочитано сегодня» на последнем фрагменте — первый и единственный
  канал записи часы→телефон (`transferUserInfo`, только добавление отметки,
  идемпотентно по дню, оптимистичное кольцо с TTL 3 дня).
- Границы постов считаются из даты Пасхи (`Shared/FastPeriods.swift`):
  колонка `fasting` календаря неполна — в ней не размечены как раз Пн–Чт
  первой седмицы.

**Новые файлы.**

- `Shared/FastPeriods.swift` — четыре многодневных поста из даты Пасхи (алгоритм продублирован из `PaschalCalculator`, т.к. `LiturgicalCalendar.swift` не входит в watch-таргет).

**Решения.**
- Акафист — единое песнопение с возвратом к 1-му икосу/кондаку после трижды читаемого 13-го; резать его по дням не на что опереться. Указание об этом показывается в листе плана дословно.
- Синодальный текст в читалке кафизм, ЦС — листом рядом: молитвослов владеет текстом, Библия — навигацией и переводом, ничего не дублируется.
- `ReaderRoute.references` не сохраняется (бросает при encode), поэтому для кафизм — свой сохраняемый маршрут.
- Тела кафизм (`psaltir`) не индексируются в FTS молитв — псалмы ищутся через поиск по Библии; названия/теги индексируются.
- «до конца поста» предлагается только если пост идёт или начнётся в ближайшие 14 дней.

**Проверено.** Контент: у всех 12 акафистов ровно 27 кондаков/икосов и указание о трижды читаемом 13-м; 20 кафизм × 3 «Славы», псалмы 1–151 без пропусков, без ЦС-глифов; итого 249 молитв, база 5,63 МБ. Самопроверки `FastPeriods` (2026: Великий пост 23.02–11.04, Петров 08.06–11.07) и совместимости снимка часов v1 — зелёные. Сборки watch/iOS/macOS. Снимки экрана: iPhone — карточка плана, лист выбора, «Мои чтения», лист «Содержание», лист Псалтири, кафизма 13 с прокруткой к «Славам», «Молитвы по кафизме», ЦС-лист; часы — строка плана на корне, экран плана 42/49 мм.

**Открыто.**

- Не снят на экране: разделитель «Слава» в читалке (нужна прокрутка), «Читать ежедневно →» внизу акафиста — проверить руками.

## 2026-07-31 — Цель: ручное кадрирование как второй заход при неузнавании

**Задача.** После съёмки, если распознавание ничего не вернуло (`.unknown`),
предложить пользователю обрезать кадр и прогнать распознавание повторно — а не
упираться в тупик «икона не найдена».

**Поведение.**
1. Съёмка → распознавание по полному кадру, как сейчас.
2. Есть ответ или подсказки — показываем результат, экран обрезки не появляется.
3. Ответа нет (`.unknown`) — экран обрезки с готовым прямоугольником и
   текстом вида «Не удалось узнать. Выделите икону — так надёжнее».
4. Пользователь правит прямоугольник → повторное распознавание по обрезке.
5. Не узнали и со второго раза — обычный экран «не найдено», без третьего круга.

**Прямоугольник по умолчанию.** Ставится автоматически:
`VNDetectRectanglesRequest`, при неудаче —
`VNGenerateAttentionBasedSaliencyImageRequest`, при неудаче обоих — 60% кадра
по центру. Берётся как есть, без расширения (обоснование ниже, в «Решениях»).

**Готово, когда.** Контрольный снимок `IMG_9467.jpeg`, не узнаваемый сегодня,
после обрезки по предложенному по умолчанию прямоугольнику отдаёт «Андрей
Первозванный, ап.» первым ответом.

**Почему — измерено, а не предположено.** Контрольное фото `IMG_9467.jpeg`
(апостол Андрей Первозванный, греческого письма, на синей стене) перестало
узнаваться. Прогон вложенной в бандл `IconClassifier.mlpackage` прямо по этому
снимку показал, что модель **не ошибается** — её отсекают пороги:

| кадрирование | softmax(Андрей) | ранг | лучший косинус в индексе прототипов | что видит пользователь |
| --- | --- | --- | --- | --- |
| как в приложении (`.centerCrop` всего кадра) | **0.360** | 1 | 0.433 | `.unknown` — пусто |
| обрезка до 80% кадра | 0.502 | 1 | — | `.unknown` — пусто |
| обрезка по доске иконы | **0.604** | 1 | 0.440 | распознано |

Андрей Первозванный — первый в списке во всех трёх случаях, с отрывом от
второго кандидата втрое. Снимок попадает в мёртвую зону: 0.360 < τ=0.60 у
классификатора и 0.433 < 0.45 у прототипов — обе проверки промахиваются
чуть-чуть и по одной и той же причине. Синяя стена занимает около трети
кадра; убрать её достаточно, чтобы вероятность выросла до 0.604 и ответ
прошёл порог. Это тот же промах распределения, что и всегда: обучающий
корпус — репродукции с pravicon.ru, где икона занимает весь кадр, а
`RandomResizedCrop(scale=(0.55, 1.0))` не покрывает случай «икона — часть
сцены».

**Решения.**
- Кадрирование предлагать именно как второй заход, а не как обязательный шаг
  перед распознаванием: в большинстве снимков рамка и так нормальная, лишний
  экран между кнопкой и ответом раздражает.
- Прямоугольник по умолчанию ставить автоматически
  (`VNGenerateAttentionBasedSaliencyImageRequest` или
  `VNDetectRectanglesRequest` — иконная доска почти всегда прямоугольник),
  чтобы обычный сценарий сводился к «подтвердить».
- Полей к прямоугольнику пользователя **не добавлять**. Первоначально
  предполагалось обратное (модель обучена на `scale` не ниже 0.55, значит ей
  нужен контекст), но замер это опроверг: на реальном снимке с широкой рамкой
  вероятность падает монотонно с каждым добавленным полем — 0.466 при обрезке
  ровно по доске, 0.267 при ×1.10, 0.125 при ×1.20, 0.048 при ×1.35 (там
  Андрей уже третий). `scale` в `RandomResizedCrop` считается от каталожной
  репродукции, которая сама обрезана по доске, поэтому тесная обрезка — это
  и есть обучающее распределение, а не выход за него.
- Усреднение по полям (TTA по нескольким паддингам) по той же причине не
  работает: 0.227 против 0.466 у одной тесной обрезки. Если делать TTA, то
  только по вариациям внутри доски, не наружу.
- Границей обрезки считать **внешний край доски**, а не край живописи и не
  прямоугольник со стеной. Замер по `IMG_9467.jpeg`: только живопись — 0.587,
  живопись +2% — 0.663, край доски — 0.606, доска +3% стены — 0.531,
  +8% — 0.519, +15% — 0.456, +30% — 0.416. Между живописью и краем доски
  плато (0.59–0.66), дальше монотонный спад, причём первые же 3% стены стоят
  дороже, чем следующие 5%. Поля доски несут надписи и ковчег — это сигнал,
  на котором модель обучена (каталожные репродукции обрезаны ровно так);
  стена — только разбавление. Значит промах внутрь дешевле промаха наружу, и
  прямоугольник `VNDetectRectanglesRequest` надо брать как есть, не расширяя.
- Порог τ=0.60 не трогать, пока нет кадрирования: он подобран на чистой
  валидации, и снижать его, компенсируя плохую рамку, — значит платить
  ложными срабатываниями по всему корпусу.

**Второй полевой снимок — кадрирования может не хватить.** Скриншот экрана
съёмки (16:16) показывает рамку заметно шире, чем `IMG_9467.jpeg`: доска
занимает примерно четверть кадра по высоте. Прогон по этому кадру:

| кадрирование | softmax(Андрей) | ранг | ранг в индексе прототипов |
| --- | --- | --- | --- |
| как в приложении (`.centerCrop`) | 0.005 | **43** | **96** |
| обрезка 80% | 0.005 | 44 | 72 |
| обрезка 55% | 0.135 | 1 | 50 |
| обрезка по доске | **0.507** | 1 | 1031 |

То есть при штатной рамке Андрея нет не только в ответе, но и близко к верху
списка — отсюда и подсказки на скриншоте результата (Купятицкая, Пафнутий
Тентирский, Распятие…), которые воспроизводятся почти в том же порядке.
Обрезка по доске поднимает его на первое место, но до 0.507 — **всё ещё ниже
τ=0.60**. Вывод: ручное кадрирование обязательно, но само по себе этот кадр
не спасает; порог придётся пересматривать вместе с ним, уже на наборе полевых
снимков, а не на чистой валидации.

**Открыто.**
- Пороги подтверждены на двух полевых снимках одного и того же сюжета; нужен
  нормальный набор «диких» фотографий, прежде чем считать τ=0.60 / 0.45
  подобранными.
- Отдельно проверить косинусный путь: на обрезке по доске классификатор
  уверенно прав (ранг 1), а индекс прототипов уводит Андрея на 1031-е место —
  эмбеддинги ведут себя не так, как логиты, и подсказки «возможно, это…»
  могут быть хуже, чем просто взять top-3 классификатора.

## 2026-07-31 — Распознавание икон: конвейер и экран доведены до рабочего состояния

**Сделано.** Функция распознавания икон по фото собрана целиком и собирается:
офлайн-обучение, экспорт модели, база метаданных, экран съёмки и результата.
Модель — 64.8% top-1 при τ=0.6. Ниже порога вместо ответа показываются
подсказки из индекса прототипов («возможно, это…»). Изменения на момент
записи не закоммичены.

**Новые файлы.**
- `RussianOrthodoxReader/IconRecognition/IconRecognizer.swift` — обёртка над Core ML-классификатором, пороги и разбор результата.
- `RussianOrthodoxReader/IconRecognition/PrototypeIndex.swift` — косинусный поиск по эмбеддингам для сюжетов ниже порога.
- `RussianOrthodoxReader/IconRecognition/IconMetaRepository.swift` — чтение справок о сюжетах из `icon_meta.sqlite`.
- `RussianOrthodoxReader/IconRecognition/IconScanView.swift` — экран съёмки.
- `RussianOrthodoxReader/IconRecognition/IconResultView.swift` — экран результата с альтернативами.
- `RussianOrthodoxReader/ScreenshotMode.swift` — детерминированное состояние для съёмки скриншотов в App Store.
- `Tools/icon_ml/09_scrape_azbyka.py` — сбор описаний сюжетов с Азбуки.
- `Tools/icon_ml/10_build_meta_db.py` — сборка `icon_meta.sqlite`.
- `Tools/icon_ml/11_verify_release.py` — проверка консистентности артефактов перед вкладыванием в бандл.

**Решения.**
- `IconRecognizer.shared` сделан опциональным (`nil`, если артефактов нет в
  бандле), чтобы приложение собиралось и работало без ML-файлов — они
  тяжёлые и не всегда лежат в чекауте.
- Классификатор ограничен iOS (`Vision`/`UIImage`), а `PrototypeIndex` и
  `IconMetaRepository` оставлены кроссплатформенными — macOS-сборка не должна
  ломаться из-за камеры.
- Старые `Resources/Icons/icon_feature_*` удалены: их заменили
  `Resources/IconML/icon_prototypes.f32/.json`, собранные стадией 08.

**Грабли.**
- Скрапер Азбуки требует пина IP — без него сыпется на середине выгрузки.
- MPS-бэкенд при обучении нужно явно гасить в конце, иначе процесс висит на
  выходе.

**Открыто.** Не проверено на «диких» фотографиях — снятых в храме, под углом,
с бликами и в неровном свете. Пороги τ=0.60 / cosine 0.45 подобраны на
чистом валидационном наборе и почти наверняка потребуют правки после полевой
проверки.
